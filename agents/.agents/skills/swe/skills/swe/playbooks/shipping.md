### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.** Landing requires the user's explicit authority. Read [Merge and restack safety](../references/merge-safety.md) before merging, arming, rebasing or retargeting.

1. **Resolve the forge, then verify each PR independently before it lands.** Use gh for every GitHub operation. Record the affected chain's repository, head SHA, base branch and SHA, and intended destination. Inspect both pending merge mechanisms and cancel ungated requests before a lengthy review, using the safety reference. Record each independent verdict's head SHA, base SHA, base branch and stable patch-id of its base-to-head diff. One verifier per PR, each an isolated worker in the active harness, runs the change the way a user would with the matching control skill (such as the available surface-driving tools), parent against head, and posts `PASS`, `PASS+NOTES`, or `FAIL` on that PR. Only a verdict from an agent that did not write the code counts, because an author checks what it meant to build. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. Patch identity is necessary but not sufficient: changes to the base, callers or dependencies require the affected checks and independent verification to run again. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted.
4. **Land bottom-up, one PR at a time.** Always merge the run's lowest unmerged PR, with `gh pr merge <pr> --repo <owner/repo> --squash --match-head-commit <verified-head>`. Confirm the destination immediately before the request; the head condition does not guard the base. If the service cannot enforce the verified head, stop at merge-ready. On GitHub a PR whose base is still its parent's branch merges into that branch, not trunk. Read the PR back for the result (`gh pr view <pr> --json state,mergedAt,baseRefName`), because a merge command can report success when a merge queue only queued the PR, and a requested auto-merge is not a merge. A landed PR reads merged with trunk as its base, not its parent's branch. Inspect the final head and merge commit, fetch the destination and confirm that commit is in its history before advancing. Arm `--auto` or admit a required merge queue only behind existing repository rules that enforce the independent verdict and required CI on the eventual revision and merge context. A current prose verdict is insufficient. Never bypass protection or use `--admin`. Before any push, rebase or base edit, inspect and cancel pending requests for every affected PR using the safety helper. Require `cancelled`; otherwise stop and reconcile. After a merge lands, retarget the child to trunk (`gh pr edit <pr> --base <trunk>`), replay only the child's commits from the recorded old-parent boundary onto the confirmed merge result, and push with an explicit `--force-with-lease=refs/heads/<child>:<captured-remote-head>` as in the safety reference. The verdict covers the patch, not its commits, so step 3's patch-id rule decides whether the verdict survives. Merge it once its checks pass and its verdict survives.
5. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment, verdict or not. On GitHub, watch the run with the queued watcher from `playbooks/babysit.md` (`scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom-to-top>`) under the available wake scheduler until it reports `COMPLETE` at the ceiling. A base that moves to trunk when its parent merges is expected, not damage to repair. At each wake compare the landing revision, including the base SHA, with the approved record and cancel pending requests whose evidence no longer applies. Preserve watcher blocker reasons and never rearm an unchanged blocker. If a merge stalls, find out why before you change anything.
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what landed and how you confirmed it, and what the next gap needs.
